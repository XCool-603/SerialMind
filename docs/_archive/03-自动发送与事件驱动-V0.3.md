# SerialMind V0.3 自动发送与事件驱动规则

> **这篇补的是什么**：V0.1 只有"手动点发送 + 简单定时发送"。真实调试里大量帧是**自动发**的——心跳、车上线握手、收到查询自动回、超时自动重发。这不是"定时发送"的加强版，而是一套**事件驱动规则引擎**。

## 1. 核心模型：规则（常驻） + 场景（一次性）

```
触发器 Trigger ──▶ 动作 Action
   │                  ├─ 发送报文
   │                  ├─ 执行场景（上线初始化序列就是场景）
   │                  ├─ 启停其他规则（链式）
   │                  ├─ 置信号值 / 告警 / 断言
   │                  └─ 延时后再执行
```

**规则 vs 场景的分工**

|      | 规则 Rule            | 场景 Scenario     |
| ---- | ------------------ | --------------- |
| 生命周期 | ，连接期间一直生效          | ，执行完结束          |
| 触发   | 周期 / 条件 / 收到帧 / 超时 | 手动、规则、CLI、测试用例  |
| 典型   | 心跳、自动应答、超时告警       | 上线初始化、取货流程、回归用例 |

**关键设计**：规则的 Action 可以是"执行一个场景"。于是"车上线 → 发握手 → 等应答 → 配模式 → 启动心跳"这种多步流程，用 **触发器 + 场景** 就能完整表达，不需要两套机制。

***

## 2. 触发器类型

| 类型             | 语义                | 例子                 |
| -------------- | ----------------- | ------------------ |
| `every`        | 固定周期              | 心跳 1000ms          |
| `onConnect`    | 链路打开成功            | 打开串口后立即发握手         |
| `signalEdge` ★ | 信号边沿（上升沿/下降沿/双边沿） |                    |
| `signalLevel`  | 信号持续满足（按周期重复）     | 温度 >80 时每 500ms 报警 |
| `signalChange` | 任意变化 / 超阈值 / 变化率  | 车速变化 >5 才发         |
| `onFrame` ★    | 收到匹配的报文           | 收到查询帧 → 自动回状态帧     |
| `timeout` ★    | 期望的响应 N ms 未到     | 心跳应答超时 → 重发        |
| `fromScenario` | 由场景显式触发           | 场景里 send:          |
| `external`     | 手动 / CLI / HTTP   | 产线工装触发             |

**边沿 vs 电平必须区分**：`车上线` 这种信号如果用电平触发，会每个周期狂发；用**上升沿**才只发一次。这是规则引擎最容易做错的地方，UI 上要显式让用户选。

***

## 3. 动作类型

| 动作                 | 说明                                 |
| ------------------ | ---------------------------------- |
| `send`             | 发送某报文，参数可绑：常量 / 信号当前值 / 表达式 / 自增长器 |
| `reply`            | 在"收到帧"触发器下回一帧（可加延迟、可注入错误）          |
| `runScenario`      | 执行一个场景（上线初始化就用这个）                  |
| `start` / `stop`   | 启停其他规则（链式编排）                       |
| `setSignal`        | 置本地信号值                             |
| `alert` / `assert` | 告警 / 断言                            |
| `delay`            | 延时后继续                              |

## 4. 三个真实例子（可直接对照你的项目）

### ① 心跳

```yaml
rule: heartbeat
link: plc-to-vehicle
trigger: { every: 1000ms }
action:
  send:
    message: heartbeat
    params: { seq: auto, status: "$signal(vehicle.status)" }
expect:                                   # ★ 心跳不是单向广播，是请求-响应
  response: heartbeat_ack
  timeout: 300ms
  retry: 2
  onFail: { after: 3, do: [alert: "链路心跳中断", markLinkDown] }
```

**心跳要做完整闭环**：发 → 等 ACK → 超时重试 → 连续失败 N 次告警/标红链路。只发不等 ACK 的"心跳"是假心跳，排障时毫无价值。

### ② 车上线自动发（你举的例子）

```yaml
rule: vehicle-online-handshake
link: plc-to-vehicle
trigger:
  primary:  { signalEdge: { signal: vehicle.online, from: 0, to: 1 } }  # 上升沿，只触发一次
  fallback: { firstFrameOnLink: any }                                    # 收到该链路第一帧也视为上线
action:
  runScenario: init-vehicle
cooldown: 2s                                                             # 防抖，避免反复上线反复初始化
```

```yaml
scenario: init-vehicle
steps:
  - send: { message: login, params: { id: "$config.stationId" } }
  - wait: { response: login_ack, timeout: 500ms }
  - send: { message: set_mode, params: { mode: DEBUG } }
  - start: { rule: heartbeat }        # 握手成功后自动启动心跳
  - start: { rule: status-poll }
```

**"车上线"到底怎么判定？** 三种检测方式，按可靠性排序，建议组合使用：

| 方式      | 说明               | 可靠性        |
| ------- | ---------------- | ---------- |
| 链路首帧    | 该链路上出现第一帧符合协议的报文 | 高（不依赖业务定义） |
| 在线信号上升沿 | 车端上报的在线状态 0→1    | 高（语义最准）    |
| 心跳恢复    | 心跳断了又恢复          | 中（会延迟发现）   |

### ③ 自动应答（我扮演其中一端）

```yaml
rule: auto-answer-query
link: plc-to-vehicle
mode: simulate                       # 我扮演车端
trigger:
  onFrame: { message: query_status, match: { addr: "$self.addr" } }
action:
  reply:
    message: query_resp
    delay: 5ms                       # 模拟设备处理耗时
    params:
      position: "$signal(vehicle.position)"
      speed:    "$signal(vehicle.speed)"
```

这条规则同时服务于两个场景：**调试时假装下位机**，以及**自动化测试时对端模拟**。

## 5. 发送调度（决定"稳不稳"）

| 机制   | 规则                              |
| ---- | ------------------------------- |
| 优先级  | 手动 > 场景 > 触发规则 > 周期心跳（可配）       |
| 队列   | 单链路 FIFO + 优先级插队；队列深度可配，溢出告警    |
| 去抖   | 信号触发类规则强制 cooldown（默认 500ms）    |
| 限流   | 全局最大帧率（默认 200 帧/s）+ 单规则最小间隔     |
| 风暴保护 | 同一规则 100ms 内重复触发只执行一次，记录丢弃计数并显示 |
| 边沿默认 | 信号条件默认，避免周期性狂发                  |

## 6. 来源标记（调试可见性，别小看）

自动发的帧必须和手动发的帧**在视觉上分得开**，否则调试时因果全乱。终端行前缀标记：

| 标记   | 来源        |
| ---- | --------- |
| `⌨`  | 手动发送      |
| `⏱`  | 周期（心跳/定时） |
| `⚡`  | 条件触发      |
| `🎬` | 场景执行      |
| `🤖` | AI 指令     |
| `↩`  | 自动应答      |

终端支持按来源过滤（"只看手动发的"），检查器里也能看到"这帧是哪条规则发的、第几次命中"。

## 7. 安全红线（自动发送会动真设备）

* **顶栏自动发送总开关**，醒目可一键全停（默认建议：连接后提示开启，而非默认全开）。
* **危险命令拦截**：写寄存器 / 复位 / 升级 / 运动控制类报文，在自动发送规则里命中时默认**拦截**，需显式勾选"允许自动发送危险命令"。
* **首次运行预览**：新规则启用后先"预览 3 秒"（只显示将发什么、不发），确认再真发。
* **监听模式下强制禁用自动发送**（监听就不该发言，否则污染现场总线）。
* **物理安全文案**：车类项目要在规则启用时明确提示"自动发送可能导致车辆动作，请确认现场安全"。
* **录制回放交互**：回放时默认**不重放**自动发送规则（只回放录制帧），可勾选"重放规则"复现完整现场。

## 8. UI：规则面板

```
规则                     触发                 动作                状态
──────────────────────────────────────────────────────────────────────────
⏱ 心跳                   每 1000ms           发心跳帧 + 等 ACK   运行中 · 命中 3600
⚡ 上线握手               车在线 0→1（上升沿）  执行"初始化"场景    等待中
↩ 查询应答               收到 0x03 查询       回状态帧（延迟 5ms） 运行中 · 命中 812
⏱ 状态轮询               每 200ms            发查询帧            运行中
⚠ 心跳超时告警           心跳 ACK > 300ms    告警 + 标记链路异常  正常（0 次）
```

* 每行独立开关；顶部"全部暂停"；命中次数与上次触发时间实时刷新。
* 点任意规则 → 右侧显示"最近 10 次触发记录 + 每次发的原始字节"。
* 规则可从**协议模板**一键生成（Modbus 的"周期读寄存器"、心跳帧等）。

## 12. 开放问题（新增）

* **心跳是否需要设备回 ACK？** 如果需要，ACK 帧格式要定；如果只是单向广播，那"链路健康度"就只能靠别的信号判断。
* **"车上线"你现场实际靠什么判定？** 链路首帧 / 在线信号 / 心跳恢复——我默认前两者组合。
* **自动发送默认开还是默认关？** 我倾向默认关 + 连接后提示，避免误动设备。
* **危险命令清单**要不要由项目配置（不同设备"危险"定义不同）？我倾向做成项目级可配。
* 仍未答：**链路是点对点还是 RS485 总线多点**、**自动化测试跑在哪**、**车辆项目是否 CAN**。
