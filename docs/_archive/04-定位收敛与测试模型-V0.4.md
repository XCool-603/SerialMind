# SerialMind V0.4 定位收敛：以自动化测试为唯一目标

> **本文修正 V0.2 / V0.3 的跑偏**：那两篇把"业务语义建模"当成了产品核心（设备角色、链路拓扑、模拟器、链路健康度……）。实际上——**它就是一个 SScom，跟硬件没有任何关系**。工具只认串口上的字节，不需要知道对面是什么。**所有功能存在的唯一理由：自动化测试。**

***

## 0. 我跑偏在哪（先认账）

| 我写进 V0.2/V0.3 的          | 问题                           |
| ------------------------ | ---------------------------- |
| 设备角色（PLC / 伺服 / 上位机 / 车） | 工具凭什么要知道对面是什么？加了这个就要维护一堆业务语义 |
| 链路拓扑、点对点/RS485 总线建模      | 一个串口就是一个串口，不建模拓扑             |
| 监听 / 模拟 / 主控 三种工作模式      | 过度设计，用户只是"要不要发"而已            |
| 链路健康度、RTT 统计、断链告警        | 这是设备管理平台该干的事，不是串口工具          |
| 模拟器（设备行为脚本）              | 本质就是"收到 X 回 Y"，规则引擎已经覆盖      |
| 信号多来源优先级选择               | 字段就是字段，一个字段一个来源，别搞虚的         |
| 数字孪生、项目模板                | 项目只是配置容器                     |

**根因**：我从"你要调起重机和小汽车"推演出了一个"工业设备管理平台"，而你要的是"一个能自动跑测试的 SScom"。方向错了，功能越多越偏。

***

## 1. 重新定位

> **一个能自己跑起来的 SScom。**
> 协议和用例配一次，之后每次改完固件，点"跑一遍"，它告诉你哪条没过、字节差在哪。

### 三条边界（硬件无关）

| 边界            | 含义                                                            |
| ------------- | ------------------------------------------------------------- |
| **只认通道，不认设备** | 工具眼里的世界只有"一个串口 + 一串字节"。对面是什么，最多写个备注文本，                        |
| **项目只是文件夹**   | "起重机项目""小汽车项目"= 两套互不干扰的协议 + 用例 + 配置。切换项目 = 切换一组配置，不切换任何"硬件模型" |
| **一切为了少动手**   | 能自动发的不要手动点；能自动断言的不要人眼看；能自动重跑的不要人守                             |

### 一句话说清它和 SScom 的关系

**功能上是 SScom 的超集，定位上比 SScom 更窄**——SScom 让你"能看到、能发出"，SerialMind 让你"不用看、不用发，跑完给结论"。

## 2. 简化后的对象模型（4 层，替代 V0.2 的五层）

```
项目 Project            ← 纯配置容器（起重机 / 小汽车）
├── 协议 Protocol        ← 帧格式定义（PDL）：字段、校验、分帧
├── 通道 Channel         ← 一个串口 + 参数 + 绑定协议 + 备注（自由文本）
│     └── 报文 Message   ← 协议里的帧类型
├── 自动发送规则 Rule     ← 心跳 / 周期 / 触发 / 自动应答（让通道"活着"）
└── 测试 Test            ← 用例 → 套件 → 运行 → 报告
```

| 层      | 是什么                    | 不是什么              |
| ------ | ---------------------- | ----------------- |
| **项目** | 一组配置的命名空间，可导出/导入/进 Git | 不是硬件拓扑图           |
| **协议** | 字节 ↔ 字段的翻译规则           | 不绑定任何具体设备型号       |
| **通道** | 一个串口句柄 + 参数 + 一个备注字符串  | 不是"设备"，没有角色，没有健康度 |
| **规则** | 什么时候自动发什么              | 不是"设备模拟器"         |
| **测试** | 步骤 + 断言 → 通过/失败        | 不是"场景编排业务流"       |

**字段即变量**：协议里的字段可以直接在用例里断言、可以参数化、可以被数据发生器驱动。不再单独造一层"信号字典"。

> 唯一保留的"复杂"是**字段级的拆合**（高地位、跨字段拼装、位段提取、字节序四选一）——因为这是真实字节里客观存在的，不是业务语义。

## 3. 核心：自动化测试模型（这才是产品本体）

### 3.1 用例 = 步骤序列 + 断言

```yaml
case: 从1号点位到3号点位
channel: ch1
steps:
  - set:    { field: target_point, value: 3 }        # 改字段值 → 自动组包发送
  - expect: { field: position,    equals: 3000, within: 3s }
  - expect: { field: in_position, equals: 1,    within: 200ms }
  - expect: { field: mode,        equals: PICKING }
  - assertNo: [crc_error, timeout, unexpected_frame]
```

### 3.2 步骤类型（少而够用）

| 步骤         | 作用                         |
| ---------- | -------------------------- |
| `send`     | 发一个报文（原始 HEX 或按字段填参）       |
| `set`      | 改一个字段值并自动组包发送（最常用，省去算 CRC） |
| `expect`   | 等待并断言（带超时）                 |
| `delay`    | 纯延时                        |
| `loop`     | 重复 N 次（稳定性/压力）             |
| `parallel` | 并行下发多个字段（）                 |
| `call`     | 调用子用例（公共流程复用）              |
| `script`   | JS 逃生舱（复杂计算/自定义判据）         |

### 3.3 断言类型

| 类型      | 说明                             | 例子                    |
| ------- | ------------------------------ | --------------------- |
| 字段值     | equals / range / in / 位段 / 变化率 | position == 3000      |
| **字节级** | 整帧字节完全匹配                       | 校验算法回归（改代码后 CRC 不能变）  |
| 时序      | within（T 内到达）/ 周期稳定 ±X ms / 顺序 | position 在 3s 内到 3000 |
| **无异常** | 无 CRC 错 / 无超时 / 无越界 /          | 期望收 1 帧却收 3 帧 → 失败    |
| **容错率** | N 次里至少 M 次成功                   | loop 100 次，成功率 ≥ 99%  |

### 3.4 数据驱动

```yaml
case: 点位联动回归
data: points.csv
steps:
  - set:    { field: target_point, value: "$row.point" }
  - expect: { field: position, equals: "$row.expect_pos", within: 3s }
  - expect: { field: mode,     equals: "$row.expect_mode" }
```

```csv
point,expect_pos,expect_mode
1,1000,PICKING
2,2000,PICKING
3,3000,PICKING
```

一份用例 × N 行数据 = N 次执行，报告按行汇总。**这是把"测 100 个点位"从 100 次手动变成 1 次点击的关键。**

### 3.5 执行与报告

| 能力                 | 说明                                              |
| ------------------ | ----------------------------------------------- |
| 单步调试               | 像调试器一样一步步执行，每步看实际收发与字段值                         |
| 跑用例 / 跑套件 / 循环 N 次 | 冒烟（10 条 1 分钟）/ 全量 / 稳定性长跑                       |
| 失败策略               | 失败即停 / 继续收集所有失败（默认后者）                           |
| **失败现场** ★         | 自动保存失败前后 N 秒的收发记录 + 期望 vs 实际 + 原始字节高亮差异         |
| 一键复跑               | 报告里点单条失败用例直接重跑（保留现场）                            |
| 报告                 | HTML 单文件可分享：通过率、耗时、失败原因、字节对比、一键复跑；同时出 JUnit XML |

### 3.6 回归（这才是"自动化测试"的日常形态）

* **固件回归**：改完固件，一键跑全套 → 与上次结果 **diff**（哪些从过变不过、哪些新增失败）
* **协议回归**：协议定义改了 → 自动列出引用它的用例并重跑（防止改协议把用例搞坏）
* **CI**：`serialmind test run suite.yaml --channel COM3 --report out.html --junit out.xml --headless`

## 4. 自动发送（重新定位：为测试服务，不是设备管理）

保留 V0.3 的规则引擎，但**目的收窄**：

| 规则        | 在测试里的作用                      |
| --------- | ---------------------------- |
| 心跳 / 周期轮询 | 让被测系统保持"活着"的常态，否则测到一半它自己超时断链 |
| 自动应答      | 被测系统问过来时要有人答，否则用例卡住          |
| 条件触发      | 构造特定前置状态（如"车速 > 0 时才允许挂挡"）   |
| 超时重发      | 复现真实链路的容错行为                  |

**砍掉**：链路健康度、断链告警、RTT 统计、"监听/模拟/主控"三模式。只留一个勾选：**"只接收不发送"**（用于纯抓包场景）。

**保留**：来源标记（`⌨`手动 / `⏱`周期 / `⚡`触发 / `🎬`用例 / `↩`应答）——否则测试报告里的帧分不清是谁发的。

## 5. AI 的新定位（全部指向"少写、少查"）

| 能力                | 价值                                                     | 优先级    |
| ----------------- | ------------------------------------------------------ | ------ |
| **协议文档 → PDL**    | 不用手写协议（最大痛点）                                           | P0     |
| **自然语言 → 测试用例** ★ | "测一下 1 号点位走到 3 号点位，位置 3 秒内必须到 3000，到位标志必须置 1" → 直接生成用例 |        |
| **失败分析** ★        | 读期望 vs 实际 + 原始字节，给"可能原因"                               | P1     |
| 自然语言组包/发帧         | 调试时临时用                                                 | P2（降级） |
| 实时流异常分析           | 有规则引擎兜底，AI 是锦上添花                                       | P2（降级） |

**AI 用例生成是这次的重点补充**——既然目标就是自动化测试，那 AI 最该帮的是"把一句话变成一条可执行用例"，而不是"帮我发一帧"。

## 8. 开放问题（只剩这些）

* **测试结果怎么判"对"？** 你现在人工验证时看的是什么——某个字段的值、还是整帧字节、还是设备动作（比如车真的动了）？这决定断言类型的主次。
* **用例谁来写？** 你自己写，还是希望 AI 从一句话生成后你再改？
* **要不要"设备动作"这种外部结果参与判定？**（比如车动没动、货取没取到）如果要，就得留人工确认点，不能全自动。
* 链路是点对点还是 RS485 一主多从？（仍影响一个通道能不能挂多个从站地址）
