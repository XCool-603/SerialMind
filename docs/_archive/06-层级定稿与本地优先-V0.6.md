# SerialMind V0.6 层级定稿与本地优先

> **这篇定三件事**：① 层级定稿（产品为主、链路为辅、客户即租户）；② 本地优先的确切含义；③ **为将来云端预留什么**——不做功能，只做不给自己挖坑的六件事。

***

## 1. 已确认的决策

| # | 决策 | 说明                      |
| - | -- | ----------------------- |
| 1 |    | 产品是主导航单位、配置归属单位、导出单位    |
| 2 |    | 链路是产品下的附属资源，与协议/规则/用例同级 |
| 3 |    | 客户在数据模型里就是 tenant       |
| 4 |    | V1 不做账号、不做云端、不做多租户服务端   |
| 5 | 云端 | 以后再说，但                  |

***

## 2. 层级定稿

```
租户 Tenant（客户）        V1 固定为 local，仅作数据字段存在
└── 产品 Product  ★主导航   起重机 / 小汽车
    ├── 链路 Link   （辅）   COM3 起升PLC · COM5 小车PLC
    ├── 协议 Protocol
    ├── 规则 Rule
    ├── 用例 Case
    └── 套件 Suite
```

### "产品为主"具体体现在三处

| 体现        | 说明                                               |
| --------- | ------------------------------------------------ |
| **导航主单位** | 顶栏是产品切换器，切换产品 = 整套配置全换（互不干扰）                     |
| **配置归属**  | 协议/规则/用例都挂在产品下，；要复用就复制一份过去                       |
| **导出单位**  | 一个 .smprod = 完整可交付物（链路+协议+规则+用例+套件），可发给同事、可进 Git |

### "链路为辅"具体体现在

* 左侧树里链路是产品下的**一类资源**，不是独立入口；
* 一个产品可挂多条链路（同时开多个串口），用例指定跑在哪条链路上；
* 链路只有物理参数 + 绑定协议 + 一个备注字符串，**没有角色、没有拓扑、没有健康度**。

***

## 3. 本地优先的确切含义

| 维度   | V1 的做法                     |
| ---- | -------------------------- |
| 存储   | 本地 SQLite + 本地文件（录制、导出、日志） |
| 账号   | 。无登录、无注册、无 token           |
| 网络   | （AI 调用除外，且可完全关闭）           |
| 使用方式 | 单机单人，不需要协作/权限/冲突解决         |
| 数据归属 | 数据在用户自己机器上，卸载前导出即可带走       |

> 这条很重要：**没有 AI、没有网，它必须是一个完整好用的串口工具 + 测试工具。**

***

## 4. ★ 为云端预留的六件事（成本 < 3 天，省掉将来一次大迁移）

不做任何云端功能，只做"将来加的时候不用改表结构"的几件事：

| # | 预留项 | 做法                                                 | 为什么                  |
| - | --- | -------------------------------------------------- | -------------------- |
| 1 |     | 全表主键不用自增整数                                         | 将来多机合并不冲突；v7 天然按时间有序 |
| 2 |     | 所有业务表带 tenant\_id，V1 固定写 local                     | 将来上云端不用改表、不用数据迁移     |
| 3 |     | 存 UTC，显示时转本地时区                                     | 多机同步的前提              |
| 4 |     | created\_at / updated\_at / deleted\_at / rev（版本号） | 软删除 + 冲突检测 + 增量同步的基础 |
| 5 |     | .smprod 头部写 schemaVersion + tenantId               | 向前兼容，将来导入时能识别来源      |
| 6 |     | 所有读写集中在一层，不散落 SQL                                  | 将来换"本地实现 / 远端实现"只改一层 |

这六条加起来 **< 3 天**，但能省掉将来一次伤筋动骨的重构。

## 5. V1 明确不做

* ❌ 账号体系、登录、注册、密码找回
* ❌ 云端存储、多端同步
* ❌ 团队协作、权限、审批
* ❌ 多租户服务端
* ❌ 计费

***

## 6. 将来上云端的最小路径（备忘，现在不做）

因为本地已经有 UUID + tenant\_id + rev + 带版本号的导出格式，将来上云端**不是架构重构，是加一层**：

* 加"登录 + 租户绑定"
* Repository 加一个 Remote 实现（本地优先，冲突用 `rev` 比较）
* **同步粒度是产品级**（不是行级）：一个 `.smprod` 整体 push / pull
* 冲突策略：产品级"谁新谁赢 + 冲突时另存一份"

> 换句话说：V1 的每一个设计决定，都不影响将来加云；这才是"先本地打好"的正确姿势。

## 9. 开放问题

* **产品之间要复用协议吗？** 现在设计是"不跨产品共享，要复用就复制"。但起重机的协议可能小汽车也用——如果要共享，得加一个"公共库"层。
* **租户将来是"一个客户一台机器"还是"一个客户多台机器"？** 影响将来同步策略，不影响现在。
* 上一轮还没答的：一个产品下**同时开几条链路**、**用例自己写还是 AI 生成**、**协议改字段名旧用例怎么办**、**测试结果怎么判对**。
