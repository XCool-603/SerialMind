# SerialMind V0.2 增补：项目 · 链路 · 信号联动 · 自动化测试

> **这篇补的是什么**：V0.1 只回答了"一个端口 + 一个协议 + 手动发帧"。真实工程是"多个项目、每项目多条硬件链路、关心的是业务信号怎么联动、最后要能自动跑回归"。V0.2 补上这一整层。
> **关系**：本文是对 V0.1 的**增补与修订**，不重复 V0.1 已有内容。

***

## 0. 问题陈述：V0.1 漏了什么

V0.1 的对象模型是 `会话(端口) → 协议 → 报文`，本质是"**设备视角**：我在调试某一个口"。

但你描述的真实场景是这样的：

| 真实现象                                   | V0.1 缺的能力                  |
| -------------------------------------- | -------------------------- |
| 团队同时维护**多个项目**（起重机、小汽车…），每个项目一套硬件拓扑    | 没有"项目"这个容器，配置散落在各个会话里      |
| 一个项目里有**多条硬件间链路**：PLC↔伺服、PLC↔车、PLC↔HMI | 只有"端口"，没有"链路"和"链路两端是谁"     |
| 真正要调的不是字节，是**业务信号**：起升高度、车速、车辆位置、工作模式  | 没有"信号"这一层，字节和业务语义之间断开了     |
| 车到某个点位 → **位置/到位标志/允许取货 三个值同时变化**      | 没有"联动"，只能一条条手敲             |
| 一个 32 位量常被拆成**高低两个 16 位寄存器**，甚至分两条报文   | 没有"跨字段/跨报文拼装"能力            |
| 要造数据：**车速自增长、里程累加**，模拟上位机或下位机          | 没有数据发生器，只能手改数值             |
| 最终要的是**自动化回归**，不是人肉点按钮                 | 有测试用例雏形，但没有场景/断言/数据驱动/报告闭环 |

> **结论**：缺的不是几个功能，是**一整层对象模型**——`项目 / 设备 / 链路 / 信号 / 场景`，以及建立在其上的**联动编排**、**数据生成**、**自动化测试**。

## 1. 对象模型：五层 + 一个横向层

[untitled]()

| 层  | 对象 | 一句话                     | 起重机示例                       |
| -- | -- | ----------------------- | --------------------------- |
| L0 |    | 一个被测算系统的数字孪生描述          | "1号门式起重机"                   |
| L1 |    | 挂在链路上的一个节点，有角色和地址       | PLC(站1)、起升变频器(站2)、安全控制器(站5) |
| L2 |    | 两个（或多个）设备之间的物理通道 + 绑定协议 | RS485 主从总线、PLC↔HMI 的 TCP    |
| L3 |    | 链路上的一次传输，用 PDL 解成字段     | 状态查询、控制指令、周期上报              |
| L4 |  ★ | 有业务语义、有单位、可读可写的变量       | 起升高度(mm)、小车位置、载重、工作模式       |
| L5 |  ★ | 跨链路跨设备的条件-动作编排          | "车到3号点位取货"                  |

**关键设计决策**：信号（L4）**不是** PDL 的一部分。PDL 只描述"字节怎么变成字段"；信号是"字段怎么变成业务变量"的**独立映射层**。分开的好处：一个信号可以来自多个报文，一份协议可以服务多个项目，协议升级不影响信号定义。

## 2. 项目 Project

* 一个项目 = 一个被测算系统的完整描述：设备清单、链路清单、协议库、**信号字典**、场景库、测试套件、录制数据、报告模板。
* 存储为 `.smproj`（目录 + JSON 文件），可 **Git 管理、可 diff、可评审、可分享给同事**。
* **项目模板**：内置"起重机模板 / AGV 小车模板 / 通用 PLC 模板"，新建项目时选模板改参数即可。
* 一个工作区可**同时打开多个项目**（做版本对比、新旧机型迁移）。
* 项目内所有对象都有稳定 id，供场景、测试、AI 引用。

## 3. 设备与链路

### 设备 Device

| 字段                  | 说明                                                                             |
| ------------------- | ------------------------------------------------------------------------------ |
| `deviceId` / `name` | 唯一 id 与显示名                                                                     |
| `role`              | plc / controller（车载控制器）/ servo（伺服·CSVS）/ hmi / sensor / gateway / tool（工具/上位机） |
| `address`           | 站号（RS485）/ IP:Port / CAN id                                                    |
| `links[]`           | 该设备参与的所有链路                                                                     |
| `notes`             | 型号、固件版本、现场位置                                                                   |

### 链路 Link

| 字段                | 说明                             |
| ----------------- | ------------------------------ |
| `linkId` / `name` | 如 plc-to-vehicle、plc-to-servo  |
| `type`            | serial / tcp / can(V2)         |
| `physical`        | 串口参数 / IP 端口 / 波特率等            |
| `endpoints`       | 点对点 A↔B，或总线 master + slaves\[] |
| `protocol`        | 绑定的 PDL id + 版本                |
| `mode` ★          | （见下）                           |

### ★ 三种链路工作模式（多设备项目能落地的关键）

| 模式              | 含义         | 典型场景                  |
| --------------- | ---------- | --------------------- |
| **监听 Monitor**  | 只读不发言，旁路抓包 | 现场真实系统在跑，我只需要看和记录     |
| **模拟 Simulate** | 我扮演链路中的一端  | 只有 PLC 没有车；CI 里没有任何硬件 |
| **主控 Master**   | 我主动发命令     | 单机调试、产线工装             |

> 这个三态是产品能否进入"真实项目"的分水岭：现场排障永远是**监听**，研发阶段常常是**模拟**，产线测试是**主控**。V0.1 只有"主控"。

### 项目拓扑示例

**起重机项目**

```
        ┌──────────── PLC (站1) ────────────┐
        │            │            │         │
   RS485总线      RS485总线    RS485总线   TCP
        │            │            │         │
  起升变频器(2)  小车变频器(3)  安全控制器(5)  HMI上位机
```

**小汽车项目**

```
VCU(整车控制器) ──CAN/串口── MCU(电机) / BMS(电池) / 仪表 / 上位机调试口
```

## 4. ★ 信号字典 Signal（本方案的核心增量）

信号 = 从报文里抽出来的、有业务语义、有单位、可读可写的变量。

### 信号定义

| 字段                  | 说明                                          |
| ------------------- | ------------------------------------------- |
| `signalId` / `name` | 如 crane.height / "起升高度"                     |
| `unit`              | mm、km/h、%、A                                 |
| `type`              | uint / int / float / bool / enum / bitfield |
| `scale` / `offset`  | 原始值 → 物理值：phys = raw \* scale + offset      |
| `range`             | 值域（用于断言与越界告警）                               |
| `enum`              | 枚举映射（0=IDLE, 1=PICKING, 2=FAULT）            |
| `sources[]` ★       | （见下）                                        |
| `writable`          | 是否可写（可写才能被场景/发生器驱动）                         |
| `group`             | 业务分组（起升/行走/安全/状态）                           |

### 多来源取值（解决"同一物理量在多个报文里重复上报"）

```jsonc
{
  "signalId": "vehicle.speed",
  "name": "车速", "unit": "km/h", "type": "float", "scale": 0.1,
  "sources": [
    { "link": "plc-to-vehicle", "message": "status_frame", "field": "speed_raw", "priority": 1 },
    { "link": "plc-to-vehicle", "message": "query_resp",   "field": "speed_raw", "priority": 2 },
    { "link": "vcu-to-hmi",     "message": "display_frame","field": "speed_raw", "priority": 3 }
  ],
  "valueSelection": "highest-priority-fresh"   // 或 latest / lowest-priority
}
```

取值策略可配：**优先级优先且未过期**（默认）/ 最新到达 / 指定来源。信号面板上会标出"当前值来自哪条报文"，避免排障时看错源。

### ★ 高地位（高低字节）拆合——现场最容易出错的地方

支持三种形态，**读取时自动拼、写入时自动拆**：

| 形态       | 说明                            | 例子                      |
| -------- | ----------------------------- | ----------------------- |
| ① 同帧内多字节 | 一个量占 2/4/8 字节，需指定字节序与         | 32 位高度占 4 字节            |
| ② 跨字段拆分  | 高 16 位在字段 A、低 16 位在字段 B（可不连续） | height\_hi + height\_lo |
| ③ 跨报文拆分  | 高字节在报文 1、低字节在报文 2             | 分段传输协议                  |

```jsonc
{
  "signalId": "crane.height",
  "name": "起升高度", "unit": "mm", "type": "uint32",
  "compose": {
    "order": "hi-first",
    "parts": [
      { "message": "status_1", "field": "height_hi", "bits": "15..0", "shift": 16 },
      { "message": "status_2", "field": "height_lo", "bits": "15..0", "shift": 0 }
    ]
  }
}
```

**必须内置的字节排布四件套**（Modbus 32 位值的经典坑）：

| 排布     | 字节顺序 | 别名            |
| ------ | ---- | ------------- |
| `ABCD` | 大端   | Big-endian    |
| `BADC` | 字节交换 | Byte swap     |
| `CDAB` | 字交换  | Word swap     |
| `DCBA` | 小端   | Little-endian |

现场配错这四种之一，表现就是"数值差了 65536 倍"或"高位跑到低位"——内置选择器 + 实时预览（输入已知值看字节流），能省掉大量排障时间。

另外支持：**位段提取**（`bits: "3..0"`）、**有符号补码**、**BCD 拆分**（电表/DL645 常见）。

## 5. ★ 联动与场景编排 Scenario

场景 = 一组"**条件 → 动作**"的有序编排，可嵌套、可循环、可并行，**跨链路跨设备**。

### 声明式语法（YAML 为主，后续加可视化拖拽编排）

```yaml
scenario: 车到3号点位取货
project: 小汽车项目
steps:
  - set: { signal: vehicle.target_point, value: 3 }

  - wait: { signal: vehicle.position, equals: 3000, timeout: 5s }

  - parallel:                          # ★ 多值联动：一个触发，多个信号同时变
      - set: { signal: vehicle.in_position, value: 1 }
      - set: { signal: cargo.allow_pick,  value: 1 }
      - set: { signal: vehicle.mode,      value: PICKING }
    timing: same-frame                 # same-frame | sequential(间隔 20ms)

  - wait: { signal: cargo.weight, greaterThan: 0, timeout: 2s }
  - assert: { signal: vehicle.mode, equals: PICKING }
```

### 编排能力

| 能力     | 说明                                 |
| ------ | ---------------------------------- |
| 触发方式   | 信号条件 / 时间周期 / 手动 / CLI / HTTP 外部触发 |
| 控制流    | 串行、并行、延时、重试、超时、循环、条件分支（if/else）    |
| 多值联动   | parallel 块，可配"同帧下发"或"逐帧间隔下发"       |
| 联动嵌套   | 场景可调用子场景（复用"回原点""急停"这类公共流程）        |
| 冲突检测 ★ | 两个场景同时写同一信号 → 报警并阻止（避免测试互相干扰）      |
| 执行轨迹   | 每一步的开始/结束/耗时/实际值全部记录，失败可回放         |

### 两种用法，都要支持

* **主动编排**（我在测）：我描述一个业务流程，工具自动演出来并断言。
* **被动观测**（我在看）：系统自己在跑，我定义"期望的联动关系"，工具持续校验是否成立（如"位置=3000 后 200ms 内到位标志必须为 1"）——本质是**运行时的规则断言**。

## 6. ★ 数据发生器 Generator（自增长等）

绑定到**可写信号**，按周期刷新值 → 自动组包发送。用于模拟上位机/下位机、造压力、跑耐久。

| 波形             | 参数                      |
| -------------- | ----------------------- |
| 常量             | value                   |
| **自增长 ramp** ★ | 起始值、步长、步进周期、上限、下限、、抖动   |
| 正弦 sin         | 幅值、频率、偏置、相位             |
| 阶跃 step        | 台阶表                     |
| 随机 random      | 范围、分布、是否平滑              |
| 表达式 expr       | t、sin(t)、random()、其他信号值 |
| CSV 回放         | 从录制/表格导入真实曲线回放          |

```yaml
generator: vehicle.speed
waveform: ramp
from: 0
to: 120
step: 5
interval: 100ms
onBound: bounce        # hold（停住）| wrap（回绕）| bounce（反向）| stop
jitter: 0
```

**典型用途**

* 模拟下位机持续上报 → 测上位机的曲线、告警、阈值逻辑
* 高频变化 → 压力测试，看链路与解析是否丢帧
* 耐久测试 → 自增长跑 8 小时，看被测系统是否漂移/泄漏
* 与场景协同 → 场景里 `start: generator.speed_ramp` 启停

## 7. ★ 自动化测试

用例 = **场景 + 断言 + 前置/清理**，断言的对象是**信号**，不是字节。

### 断言类型

| 类型    | 说明                          | 例子                   |
| ----- | --------------------------- | -------------------- |
| 信号值   | 等于 / 范围 / 位段 / 枚举 / 变化率     | mode == PICKING      |
| 时序    | 在 T 内到达、周期稳定 ±X ms、抖动上限、顺序  | 位置周期 20±2ms          |
| 跨链路 ★ | A 链路发出后，B 链路在 T 内响应；端到端 RTT | PLC 下发后 50ms 内车端 ACK |
| 联动 ★  | 置 A 后 B 在 T 内变为期望值          | 到位后 200ms 内允许取货=1    |
| 一致性 ★ | 同一信号在两条报文里的值一致              | 车速在状态帧与查询响应中相同       |
| 无异常   | 无 CRC 错 / 无超时 / 无越界 / 无孤儿帧  |                      |

### 数据驱动

```csv
point,speed,expect_mode
1,10,PICKING
2,20,PICKING
3,0,IDLE
```

一份用例 × 100 行参数 = 100 次执行，报告按行汇总。

### 套件与执行

* **套件分级**：冒烟（10 条 / 1 分钟）/ 全量（200 条）/ 专项（bug 回归）
* **并行**：不同链路/不同项目可并行，同一链路串行（物理约束）
* **失败现场保存 ★**：任何断言失败，自动保存**失败前后 N 秒的多链路录制 + 信号曲线 + 场景执行轨迹**，报告里一键回放——这是排障效率的关键
* **故障注入 ★**：故意注入延迟 / 丢帧 / 错帧 / 校验错，验证被测系统的容错与恢复
* **报告**：通过率、耗时、失败原因、时序图、原始报文、环境信息；HTML 单文件可分享；同时输出 JUnit XML
* **CI**：`serialmind test run suite.yaml --project crane --report out.html --junit out.xml --headless`

## 8. ★ 多链路时序视图（排障神器）

多链路同时录制 → 合并到统一时间轴 → 泳道图 + 信号曲线叠加 + 场景执行轨迹标记。

```
时间轴 ──────────────────────────────────────────────────▶
PLC→车   ├──[位置查询]─────────[响应 位置=3000]────────────
车→PLC   │         └──[到位标志=1]──────[允许取货=1]──────
信号      │ 位置 ╱╱╱╱╱ 3000 ───────────────────────────
          │ 模式  IDLE ──────▶ PICKING ─────────────────
场景      │ ①set target=3  ②wait position  ③parallel×3
```

* 点击任意报文 → 跳到原始字节与字段树
* 框选时间段 → 只看这段的所有链路交互
* 导出 PNG/SVG 直接进周报/故障单
* 这就是回答"**车到点位时，谁先谁后、哪个信号没跟上**"的界面

## 9. 模拟器 Simulator

用项目模型 + PDL + 联动规则 + 数据发生器，把某个设备"演出来"：

* 只有 PLC 没车 → 用模拟器扮演车
* 只有车没 PLC → 用模拟器扮演 PLC
* CI 里没有任何硬件 → 全模拟 + 被测代码走虚拟串口对

**设备行为脚本**：收到 X 帧 → 按规则回 Y 帧（可加延迟、可注入错误），规则可用场景语法写，也可用 JS 写复杂逻辑。

> 模拟器是自动化测试的基础设施——没有它，CI 里跑不了任何真实场景的回归。

## 12. 新增开放问题（比 V0.1 那批更关键）

* **CSVS 具体指什么？**（伺服驱动器？车载系统？某个厂商的缩写？）确认后我把它做成一等设备角色，而不是通用 `servo`。
* **链路是点对点还是 RS485 总线多点？** 总线要处理站号寻址、冲突检测、主从时序；这会明显改变链路模型的复杂度。
* **"高地位"是指高字节/低字节，还是高 16 位/低 16 位？** 现场实际用的是 ABCD / CDAB 哪种排法？我按你的实际配法做默认值。
* **联动是"我调试时主动触发"，还是"被测系统自己产生的因果，我只需观测+断言"？** 两种都要做，但优先级不同（主动编排的工作量更大）。
* **自动化测试跑在哪？** 笔记本手动 / 产线工装 / CI 服务器 → 决定 headless CLI 与报告格式的投入。
* **车辆项目是不是 CAN 总线？** 如果是，V1 要不要支持 CAN（工作量大，建议 V1.1）。
